## 3. Recommendation

- **Ship HS2_ST244_UPG_RATE default-on at 500/s (with st246's interactive exemption).** It carries essentially all of
  S's gain: vs rel69e m1 -138 ms, m2 -130, storm open p99 -50 %/-35 %, storm-bin p99 -40 %, stall s 6.3 -> 3.0, call99
  m2 650 -> ~390, and it lowers the edge's storm-second CPU peak; memory neutral. 4x scale: the bucket is global, so
  at 4x churn the steady ask rate rises — st244 counted 75-85k asks/segment at 500/s (asks repeat every poll, real
  upgrades ~38k/220 s ~ 175/s here incl. storms). Prod 4x (45-60k users) steady upgrade rate must stay well under
  500/s or every lite conn waits: before default-on, read prod's lite-upgrade rate (obs mconnLiteUpgrade per s) on
  tunnel 1 and set the default to max(500, 3x prod 4x-projected steady peak) — or scale it by cores (e.g. 100/s per
  edge core: 20 cores -> 2000/s). A paced conn only stays single-copy longer (no user-path delay).
- **Do not ship GOGC=200.** Alone it gives no clear gain (m1/m2 375/348 vs E 451/447 is inside E's own spread
  352-582; storm-bin and stall equal to E; edge storm peak 5.5-5.8 cores, 98-99 % per core = same as E) and costs
  +450 MB edge / +870 MB exit RSS max here (~x1.3/x1.4). Bounded RSS is acceptable per policy, but there is no benefit
  to buy, and at 4x users the heap (and the +40 % GOGC overhead) scales with conns on Iran's 17.5 GB.
- Caveat: n=2 per knob (+2 X), one host, edge 6 cores CPU-bound; U alone vs S both differ by < noise.
