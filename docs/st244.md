## Where the storm-second spike comes from (per-second bins + runtime trace)

1. **Not the newly opened conns.** First requests of new crowd conns ("f", ~75/s) are ~2 % of the samples; in the
   storm seconds their p99 rises like everyone's, they do not set the bin p99.
2. **It is a global stall of all established requests for ~1 s, twice per storm.** Per-second crowd bins (probe time,
   storm at el 90 = probe ~91-92): e.g. S1 `90: c50 124 / c99 371`, `93: c50 350 / c99 541`, `94: 111/401`; D1
   `92: 275/450`, `93: 96/275`; same at the second storm (142-143) in every segment (c50 240-376 ms, i.e. the
   *median* request waits +150-280 ms; sample count drops 10-20 % in that second). Mass close (drop gen at el 115/165)
   gives a smaller one (c99 350-400, c50 ~100-174). All other seconds: c50 95-100, c99 110-160.
3. **Runtime trace of the edge (T1, el 88-95, 7 s)**: runnable goroutine queue max per 100 ms ~100-370 before the
   storm; at el 91.4 a GC cycle starts (mark 160 ms, STW < 5 ms) and the queue jumps to 1500-2200 for ~1 s
   (91.4-92.4) = the first, smaller stall; at el 94.1-95.2 the queue reaches 2000-3100 while the dispatch rate falls
   from ~22k to 7-13k transitions/100 ms with no STW and no GC = the process is starved of CPU by the OS = the big
   stall (c50 x3). Box: load avg 24-42 on 20 cores during storms, top in a storm: hs2 500 %, hs2kh 450 %,
   iperf3 108 %, probe 100+50 %, lk179gen 67 %, si 16 %, sy 26 % (both tunnel sides, emulator and generators share
   one 20-core box). So on lab1 the 4x storm spike is mostly whole-box CPU saturation 2-4 s into the storm
   (6000 opens + their 6000 lite upgrades + kharej's 6000 target dials + the generator on the same cores), plus
   a storm-triggered GC cycle.
4. Mutex profile (D1, HS2_PPROF_LOCKS=10, t82-112 delta): 92 % runtime-internal locks (sched findRunnable,
   stackcacherefill / copystack of new goroutines, injectglist, timers), sync.Mutex 4 %, LinkManager not visible.
   CPU profile: mconnEdge.open 7.4 s / 30 s (0.25 core avg, ~1.2 cores in the storm seconds), of which the lite
   raw upgrade picks (rawTick -> upgradeRawPlane -> pickPlaneFast -> cs229LiteLocked) 4.7 s.

## Conclusion

- The storm-second crowd p99 on lab1 is a ~1 s global stall (median request +150-280 ms) 2-4 s into each storm, not
  a per-link queue, not LinkManager contention, not the new conns' opens. Trace: runnable queue 2000-3100 goroutines
  while the process gets ~1/3 of its normal dispatch rate = whole-box CPU saturation (both hs2 sides + emulator +
  generators on 20 cores, load avg 24-42), with a smaller stall when the storm's allocations start a GC cycle.
- st244 (pace lite upgrades 500/s + GOGC 200): 2+2 leans positive (m1 -87, m2 -24, storm open p99 -10-14 %), but
  one B segment equals A; within this lab's +-60-90 ms noise it is **not proven**. Keys stay default OFF; do not ship.
- The lab1 storm numbers (m1 260-430) are much worse than lab2's sc234 (170-310) for the same kind of binary: lab1's
  20-core box saturates in the storm. Any further storm-p99 work must first separate edge and exit CPU
  (labslot split cpusets / par209 or two hosts), else the measured cost is the box, not hs2.
