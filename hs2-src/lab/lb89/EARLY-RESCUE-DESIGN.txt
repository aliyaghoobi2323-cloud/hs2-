lb89 (b) EARLY RESCUE for blackholed paths — why a copy cannot save the in-flight requests,
and the change that can (NOT implemented in lb89).

What fails (lb84 (c), lbv81 s1): crowd failures start +8 s after a path blackholes (the probe's request
timeout ~8 s) and peak +8..+12 s: requests already in flight on the dead path at t=0, or written onto a
conn whose only sub is on that path in the first seconds (conns with a live copy elsewhere survive).

Why "give every such conn an immediate copy" does not save them:
 1. raw first sub (capMConnRaw, mconn_raw.go): the user's bytes go straight on the smux stream, no
    records and no send buffer. The upgrade to dual needs UPGRADE(Bi) read by the exit and the exit's raw
    reader to reach Bi ON THE FIRST SUB (each side reads the other's raw bytes up to the boundary there).
    On a blackholed path that never happens; a sub dying during the handshake ends the connection by
    design (lab: HS2_LB_RESCUE_RAW on lowered paths cost 14-30 crowd failures a run). So an early copy
    of a raw conn either hangs in the handshake or kills the conn sooner.
 2. records-mode single/dual subs: a light (non-striping) conn keeps no copy of what it already wrote
    (the 2 s / 16 MiB keep buffer, HS2_MCONN_STRIPE_RESEND, is for striping conns only). A new copy sub
    carries only bytes written AFTER it opens; the request (Iran->exit) or the response (exit->Iran)
    already sitting in the dead link's buffers is not resent. It helps only the NEXT request on that conn.
 The census mix depends on the load: lbv81 s1 (crowdlife 40 s) raw 5541 / single 120 / dual all-marked
 124; lb89 (a) runs (crowdlife 200 s, loss phase) raw 152 / single 200 / dual all-marked 698 / dual with a
 good copy 22678. Either way the asked design can save only requests WRITTEN AFTER the copy opens on
 records-mode conns; requests in flight at t=0 (the +8..+10 s bins) are lost with any copy. Gain is
 bounded well below the 50 % target and could not be estimated without the implementation; the
 resend below is what reaches the bulk. For records-mode light conns the existing keep buffer
 (keepSentLocked, today only m.stN > 0) could be reused: keep 2 s of chunks for light conns on marked
 links, and queue them on the early copy (mrecv drops duplicates by offset) — no wire change for them. PATH_SILENT (lb84) already showed
 the detector side: it marks exactly the blackholed path at +6.5..8.2 s with 0 false marks in 6 runs, and
 removes only the +14..+20 s tail (placement), -9 % fails, n.s.

What can reach the +8..+12 s bulk ("raw rescue resend", needs both sides, new capability bit):
 - each side keeps the last raw bytes it wrote on the first sub (per conn ring, light conns only, bounded
   e.g. 64 KiB and 10 s; light = under mDupMaxRate, so ~tens of KB per conn; cap the total e.g. 64 MiB);
 - trigger (edge): the path-silent test at ~1.5 s (>= 80 % of >= 3 counted links silent, another path
   hearing; links with bytes queued/unacked: tcpi_unacked > 0 or a non-empty smux write queue), rate
   bound of its own (not the cut budget), never for heavy / call / striping conns;
 - Iran opens a join on a good path with RESCUE(Bi_sent, Ri_recvd) instead of UPGRADE; the exit stops
   reading the raw sub at once (no boundary wait), answers RESCUE-ACK(Bk_sent, Rk_recvd) and resends its
   raw bytes [Ri, Bk) as records; Iran resends [Rk, Bi) as records; both continue in records on the new
   sub; the raw sub is abandoned (closed without RST when it dies or answers);
 - if the ring no longer holds the gap (older than the keep), fall back to today's behaviour (no rescue);
 - clear: the first byte heard on the silent path's links unmarks it; conns already rescued stay dual
   and follow lite's idle rules.
 Cost: memory for the rings, one wire message pair, a capability bit (rel58 exits ignore it -> no
 rescue, no harm). Size: ~300-400 lines + tests (handshake races vs the normal upgrade, ring bounds,
 duplicate delivery dropped by offset in mrecv). This is a protocol change; it needs its own branch and
 the A/B asked (6 blackhole events per run, n>=6 per arm).
